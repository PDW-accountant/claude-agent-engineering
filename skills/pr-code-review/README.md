# pr-code-review — LLM 코드리뷰의 출력 계약 설계

GitHub PR의 Python 모듈을 **모든 함수·소스 순서대로, 입출력 타입과 단계별 로직까지** 분석한 한국어 리포트를 강제 생성하는 스킬. 핵심은 리뷰 *내용*이 아니라, LLM이 **매번 같은 구조로** 리뷰하도록 만든 **출력 계약(output contract)** 설계다.

## 문제

LLM에게 그냥 "이 PR 리뷰해줘"라고 하면 생기는 실패:

- **diff만 보고 맥락 없이 판단** — 바뀐 줄만 보면 함수 전체 동작을 오해한다.
- **뭉뚱그림·그룹화** — "비슷한 함수들은 ~합니다"로 넘겨 특정 버그를 놓친다.
- **형식이 매번 다름** — 세션마다 리포트 구조가 달라 비교·축적이 안 된다.
- **근거 위치 없음** — "여기 문제 있어요"만 있고 파일·라인이 없어 검증 불가.

## 출력 계약 설계

이 스킬은 위 실패를 **강제 규칙**으로 하나씩 막는다.

| 설계 결정 | 막는 실패 |
|-----------|-----------|
| **Full source 강제** (diff 금지) | 맥락 없는 오판 |
| **함수별 독립 섹션 + 소스 순서** | 그룹화·누락. 리뷰어가 실제 코드와 1:1 대응 |
| **Input/Output 타입 명시** (없으면 추론) | 인터페이스 불명확 |
| **코드 인용 + 줄 단위 분해 + 표** | 뭉뚱그린 설명 |
| **위치 정보 필수** (`파일:L시작–L끝`) | 검증 불가능한 지적 |
| **중요도 태그 `[상]/[중]/[하]` + 정렬** | 우선순위 없는 나열 |

계약을 강제하면 리뷰어(모델)가 달라져도 **출력이 수렴**한다. 형식이 고정되니 리포트를 축적·비교할 수 있고, 근거가 붙으니 그대로 검증·수정에 쓸 수 있다.

## Strict Rules의 역할

`Strict Rules`와 `Common Mistakes`는 **모델이 게을러지는 지점을 미리 봉쇄**하는 장치다. LLM은 길고 반복적인 작업에서 "생략·요약·그룹화"로 도망가려는 경향이 있는데, 그 도피 경로를 각각 규칙과 반례 표로 막아 끝까지 같은 밀도를 유지하게 한다.

## 이 스킬이 보여주는 것

에이전트에게 열린 지시("리뷰해줘")를 주는 대신, **원하는 산출물의 형태를 계약으로 못박아 출력을 결정론적으로 만드는** 설계 — 프롬프트 엔지니어링을 "부탁"이 아니라 "스키마"로 접근한 사례.
